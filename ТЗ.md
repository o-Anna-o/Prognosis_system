### 4.1. Принцип работы новой версии

Новая версия должна обращаться к существующей модели точно так же, как это происходит сейчас.

Изменяется организация приложения, а не способ прогнозирования.

Последовательность:

1. Пользователь вводит параметры квартиры.
    
2. React передаёт их Django backend.
    
3. Django проверяет корректность входных данных.
    
4. Backend передаёт параметры существующему механизму прогнозирования.
    
5. Существующая модель выполняет расчёт.
    
6. Backend получает результат.
    
7. Результат передаётся frontend.
    
8. React отображает существующие таблицы и графики.
    

При добавлении нескольких квартир этот процесс повторяется независимо для каждого объекта.

Все квартиры должны прогнозироваться одной и той же существующей моделью.

Не создавай вторую реализацию модели.

Если техническая интеграция объективно требует изменения математического кода, остановись и представь обоснование. Самостоятельно изменять модель запрещено.

### 4.3. Проверка идентичности результатов

До миграции создай контрольный набор входных данных.

Для нескольких квартир зафиксируй:

- входные параметры;
    
- базовую стоимость;
    
- прогнозные значения по годам;
    
- доступные промежуточные показатели.
    

После миграции выполни аналогичные расчёты.

Результаты должны совпадать с исходной версией в пределах установленной численной точности.

Если результаты различаются, найди и исправь причину.

Миграция не считается завершённой, пока идентичность прогнозной логики не подтверждена.

Он должен отвечать за:

- уникальные UUID;

- параметры квартир;

- состояние сворачивания карточек;
    
- добавление и удаление квартир;
    
- изменение параметров.
    

Создай отдельный `ThemeContext` для управления темой интерфейса.

Не объединяй все состояния приложения в один глобальный Context.

Разделяй состояние и функции изменения состояния там, где это помогает избежать ненужных повторных рендеров.

Состояния, относящиеся исключительно к одному компоненту, оставляй локальными.

### 11.3. Управление серверными данными — TanStack Query

Используй TanStack Query для взаимодействия с Django API.

Он отвечает за:

- получение справочников;
    
- запросы прогнозирования;
    
- кэширование результатов;
    
- повторное использование данных;
    
- обработку загрузки;
    
- обработку ошибок;
    
- повторные запросы при необходимости;
    
- взаимодействие с ИИ-агентом.
    

Разделяй:

**React Context:**

- карточки квартир;
    
- параметры;
    
- порядок добавления;
    
- активные вкладки;

**TanStack Query:**

- ответы Django;

- ответы API;
    
- состояние серверных запросов.
    

Не дублируй одни и те же результаты одновременно в Context и TanStack Query.

Кэшируй прогнозы с учётом идентификатора квартиры и актуальности её параметров.

При изменении параметров одной квартиры предыдущий результат должен переставать отображаться как актуальный.

При этом результаты остальных квартир не должны сбрасываться.

- легенду;

- отображение года;
    
- отображение стоимости;
    
- масштабирование при необходимости;
    
- адаптивность.
    

Не допускай наложения и некорректного отображения линий.

## 25. ОБЩИЙ ГОРИЗОНТ СРАВНЕНИЯ

Если пользователь выбрал разные горизонты прогнозирования, сравнение должно выполняться на едином временном интервале.

Используй минимальный общий доступный горизонт среди успешно рассчитанных квартир либо предоставь пользователю возможность выбрать общий горизонт.

Сопоставляй значения за одинаковые календарные годы.

Индивидуальные вкладки продолжают показывать полный прогноз каждой квартиры.

Не сравнивай конечные значения, рассчитанные на разные периоды.

## 26. ИТОГОВЫЙ РЕЙТИНГ ПЕРСПЕКТИВНОСТИ

После графика размести блок:

**Итоговый рейтинг перспективности квартир**

Квартиры должны располагаться от наиболее перспективной к наименее перспективной.

Основной критерий — относительное изменение прогнозируемой стоимости за одинаковый период.

Формула:

Темп роста (%) = (P_end / P_start - 1) × 100.

Где:

- P_start — начальная стоимость;
    
- P_end — прогнозируемая стоимость на конец общего периода.
    

Для каждой квартиры рассчитай:

- место;
    
- улицу;
    
- начальную стоимость;
    
- конечную стоимость;
    
- абсолютный прирост;
    
- относительный прирост в процентах.
    

Сортировка выполняется по убыванию относительного роста.

### 26.1. Ограничения рейтинга

Рейтинг формируется исключительно на основании результатов существующего алгоритма прогнозирования.

Не создавай дополнительную модель для оценки перспективности.

Не добавляй искусственные коэффициенты, оценки привлекательности или факторы, не используемые текущим прогнозированием.

Если существующая модель формирует одинаковый процентный рост для нескольких квартир, присваивай им одинаковое место.

Внутри одинакового рейтинга сохраняй исходный порядок добавления квартир.

Не подменяй процентный рост абсолютной стоимостью квартиры.

Не называй прогнозируемый рост гарантированной инвестиционной доходностью.

Параметры передаются backend для прогнозирования.

Постоянное сохранение пользовательских сравнений не входит в обязательный объём разработки, если аналогичная функция уже не реализована в исходном проекте.

Если в существующем приложении есть постоянное хранение данных квартир, сохрани соответствующую функциональность.

Все сценарии прогнозирования должны обращаться к одному существующему механизму:

- прогноз одной квартиры;
    
- прогноз нескольких квартир;
    
- повторный прогноз;
    
- прогноз по запросу через ИИ-агента.
    

Не создавай параллельные реализации.

Frontend не должен самостоятельно рассчитывать стоимость.

ИИ-агент не должен самостоятельно формировать числовой прогноз.

Результаты должны поступать от существующей модели через Django backend.
